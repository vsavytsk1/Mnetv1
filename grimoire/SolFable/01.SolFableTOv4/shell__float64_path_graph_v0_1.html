The Path — float64 is a graph

Not a kind of number. A finite path graph with 18,437,736,874,454,810,624 nodes, graded edges, and a hard end. Every precision fact you know is a fact about this graph.
exactcomputed livedesign
The thesis. A floating-point format is a finite set with a successor function. That is a path graph. The nodes are bit patterns; the edge is nextafter; and — this is the part nobody draws — the bit pattern read as an unsigned integer IS the node index. Verified below, live, with a DataView.

What follows from it. Edge length doubles every octave, yet every octave holds exactly the same 252 nodes. Rounding is projection onto the path. Catastrophic cancellation is landing on a fine node while still carrying a coarse halo. Going past 15.95 digits means leaving the path: double-double is a depth-2 tree grown on it, and exact rationals are the Stern–Brocot tree, on which φ is the pure alternating walk RLRLRL… — the same alternation the golden selector prints as sign flips.

What it costs in silicon. 53 bits is a 53×53 partial-product array. 113 bits is 4.546× the cells. That ratio, not mathematics, is why your CPU stops where it stops.

IThe path — count the nodes, exactly▶
exact A binary64 has 1 sign bit, 11 exponent bits, 52 stored mantissa bits. Exponent field 2047 is reserved for ∞ and NaN. Everything else is a finite number. So the count is not an estimate — it is integer arithmetic, done here in BigInt:
all bit patterns 2^64 = 18446744073709551616 reserved (exp=2047) 2^53 = 9007199254740992 = 2 infinities + 9007199254740990 NaNs finite patterns 2^64 − 2^53 = 18437736874454810624 distinct VALUES 2^64 − 2^53 − 1 = 18437736874454810623 = +0 and −0 are two nodes, one value
That is the whole universe of float64. Eighteen quintillion nodes, and then it stops. The monkey-brain move: this is a finite object you could, in principle, list. Not a continuum that occasionally misbehaves — a bead chain with a first bead and a last bead.
Named nodes at the ends: the largest finite is ≈1.7976931348623157×10308, the smallest positive subnormal is ≈4.9406564584124654×10−324. Both are drawn from the same integer index space as every other node.
IIThe grading — every octave holds the same 2⁵² nodes▶
exactcomputed live Move the morph slider above and watch the nodes bunch toward zero. That bunching is the single most important fact about floating point, and it has an exact statement: the interval [2ᵏ, 2ᵏ⁺¹) contains exactly 2⁵² nodes for every k. Same node count. Wildly different width. The edges double at each octave boundary.
This is why error is relative, not absolute. The graph is built so that the edge beside a node is always about 2⁻⁵³ of that node's magnitude. You get the same fractional resolution at 10−300 as at 10300, and it costs the same number of beads.
ulp(1) = 2^−52 = 2.220446049250313e−16 the edge next to 1.0 digits = log10(2^53) = 15.9546 the ceiling, in decimal
The subnormals near zero are the exception, and deliberately so: below 2−1022 the spacing stops shrinking and becomes uniform. That is Kahan's gradual underflow, fought for on the 754 committee against opposition, and it is what makes x − y = 0 ⟺ x = y true. Without it, two distinct numbers could subtract to zero.
IIIThe index theorem — the bit pattern IS the node number▶
computed live The claim: for positive floats, take the 64 bits, read them as an unsigned integer, and you have the node's position along the path. Walking one step on the graph is adding 1 to the integer. This is not a coincidence — IEEE 754 orders the exponent field above the mantissa field precisely so the encoding is monotonic. Verified here with a DataView, no assumption:
Press the button in the stage to set morph = 100%. In index-space every node is evenly spaced, because you are now plotting the graph by its node number instead of by its value. The grading vanishes. It was never in the graph — it was in the embedding.
This is why the classic trick works: you can compare positive floats by comparing their bit patterns as integers, and the ULP distance between two floats is literally the integer difference of their encodings — the graph distance.
IVRounding is projection onto the path▶
exact A real number lands between two nodes. Rounding is the map ℝ → path that sends it to the nearest one (ties to even). Every arithmetic operation is therefore two steps: compute the exact real answer, then project. IEEE 754 guarantees this projection is correctly rounded for + − × ÷ and √ — and for nothing else.
Drag on the strip above. The lollipop is your real number; the drop line is where it lands. The relative error stays bounded by half an edge no matter where you go — that bound is the format's promise. sin, cos, atan, exp, pow and log get no such guarantee — ECMA-262 leaves them implementation-approximated, which is why three algebraically identical routes to one angle can differ by several ulp on one engine.
VThe halo — what cancellation actually does▶
exactcomputed live Here is the picture that fixes the intuition. Two nodes sit near each other, far from zero, each already carrying a halo of uncertainty from its own rounding — half an edge, and the edges out there are coarse. Subtract them. The answer is small, so it lands in a region where the edges are fine. But the halo does not shrink. It came along.
So you end up on a node with fifteen decimal digits printed, sitting inside a halo that spans millions of nodes. The digits are real. The information is not. That is catastrophic cancellation, and it is the whole reason a convergence-rate diagnostic dies.
exact The nuance that surprises everyone — Sterbenz's lemma: if b/2 ≤ a ≤ 2b then a − b is computed exactly, zero rounding error. Verified live:
Read that carefully, because it inverts the usual story. The subtraction is innocent. It performs perfectly. It simply reveals error that was already sitting inside the operands, promoted from invisible last digits to the leading digit. Blaming the minus sign is blaming the messenger — Higham's point, §1.7 of Accuracy and Stability of Numerical Algorithms.
VIThe escape — one real, two nodes, and the tree▶
exactcomputed live Now the way out, and it is beautiful. When you add two nodes, the exact answer lands off-path and gets projected. The roundoff — the distance you were projected — is itself exactly a node. Always. It costs six additions to recover it (Knuth's TwoSum, 1969):
s = a + b bv = s − a e = (a − (s − bv)) + (b − bv) and now a + b = s + e, EXACTLY
Verified above against BigInt exact rational arithmetic — not float-compared, which would be circular. So: one real number, represented by an ordered pair of nodes. The representable set is no longer a path. Every coarse node now carries its own fine path of possible partners, and the structure is a depth-2 tree: 53 bits at the root, 53 more on each branch, 106 bits ≈ 32 decimal digits. That is double-double. Go to depth 4 and you have quad-double, 212 bits ≈ 64 digits.
design Note what this tree does not extend: the exponent range. The root is still an ordinary float64, so double-double still overflows at 10308. You bought mantissa, not reach. And the tree is non-canonical — the same real can sit on several branches, which is why DD comparison and printing need care.
The hardware that makes this cheap is the fused multiply–add. Dekker's original exact product needed splitting into halves and 17 operations; with an FMA it is two. The same instruction the silicon added for speed is the one that lets software climb off the path the silicon built.
VIIThe silicon — why 53, and what 113 would cost▶
external The number 53 is not mathematics. It is a 1980 chip. Intel hired William Kahan to design the arithmetic for the 8087 coprocessor; the Kahan–Coonen–Stone draft became IEEE 754-1985. 64 bits was the natural double word. Eleven bits of exponent buys about 10±308, enough that ordinary physical calculations do not overflow. What remains is 52 stored mantissa bits — and normalization donates one more for free, because the leading bit of a normalized binary number is always 1 and therefore carries no information. 52 stored, 53 effective.
exact Multiplying two mantissas means a partial-product array, one cell per bit pair. The area is quadratic, and that is the whole story of why the ceiling sits where it does:
A binary128 multiplier is 4.546× the array of a binary64 one, on a datapath that is already among the largest blocks on the die, to serve a small fraction of workloads. So x86 and ARM simply do not build it. IBM z/Architecture and POWER9 do; SPARC and PA-RISC specify it; RISC-V has it as the optional Q extension. On your machine __float128 is software, and transcendentals in it run on the order of 50–100× slower than double.
The x87's 80-bit extended format — 64-bit mantissa, only 1.458× the array — was Kahan's deliberate hedge: compute intermediates wider so naive algorithms survive. It worked, and it created the classic trap, because a value living in an 80-bit register and the same value spilled to 64-bit memory are different numbers. Same source, same machine, two answers.
external And the industry's current motion is downward: bfloat16, TF32, FP8, FP4 for machine learning. Consumer GPUs deliberately cripple FP64 — an RTX 5090 does 104.8 TFLOPS at FP32 and 1.637 at FP64, a 64:1 ratio, market segmentation rather than physics. High precision is not getting cheaper. It is getting scarcer, and it is moving into software.
VIIIThe other tree — Stern–Brocot, and φ as a walk▶
exact Leave floating point entirely. Exact rationals also have a graph, and it is one of the loveliest objects in mathematics. Start with 0/1 and 1/0 as fenceposts. The mediant of p/q and r/s is (p+r)/(q+s). Insert it between them, recurse. Every positive rational appears exactly once, already in lowest terms. That is the Stern–Brocot tree, and navigating it is a string of L and R.
Now walk toward φ. At each node you go L if you overshot, R if you undershot. The walk is:
Pure alternation. R L R L R L R L… forever, because φ's continued fraction is [1;1,1,1,…] — every partial quotient is 1, the smallest possible, which is exactly what "hardest number to approximate by a fraction" means. And the nodes you land on are 1/1, 2/1, 3/2, 5/3, 8/5, 13/8, 21/13 — the Fibonacci ratios. The mediant of two consecutive ones is the next one.
computed live Compare the error column above to the golden selector in the LUCA shell. They are the same numbers: −6.180e−1, +3.820e−1, −1.180e−1, +4.863e−2, −1.803e−2… The alternating sign your HUD prints as overshoot and undershoot is the L and R of this walk. The λ = −1 eigenmode of the light matrix is a turn instruction on the Stern–Brocot tree.
And on this tree nothing rounds, nothing cancels, and nothing dies at n = 36 — because every node is an exact pair of integers and BigInt has no ceiling. The path graph has an end. This tree does not.

exact Why the exact lane cannot die: rationalising k/ℓ − φ turns the numerator into the integer (2k−ℓ)² − 5ℓ², which for a Fibonacci pair collapses to 4(−1)ⁿ — a tiny exact integer, and the alternating sign your golden HUD prints. The denominator is a sum of positives. Nothing subtracts near-equals anywhere in that lane, at any n.

The a-priori prediction is not fitted. Digits remaining ≈ 15.955 − 2·log₁₀(φ)·n, because the deviation falls like φ⁻²ⁿ and the floor is fixed at ε·scale. It crosses zero near n ≈ 38 — which is where the float lane is measured to be worthless. You can compute where the wall is before you hit it.
